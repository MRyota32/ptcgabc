# LLM役割分担とハンドオフ入力文書の作法

複数のAIセッションを役割分担させて回すプロジェクト（例：ポケカABC＝Cowork=作る／ハーネス環境=測る／Fable=考える・書く）で、セッション間の引き継ぎを劣化させないための文書規約。実際のプロジェクトで確立・運用したもの。

## 大原則

1. **1文書=1目的**。レビュー依頼・戦略立案・実装依頼を1枚に混ぜない。目的が違えばプロンプトの縛りも違う。
2. **自己完結**。受け手は文脈ゼロと想定し、必要な事実は全部文書内に埋め込む。「前回の会話参照」は禁止（受け手には見えない）。
3. **本文=コンテキスト、末尾=コピペ用プロンプト**の2部構成。プロンプトはコードブロックで囲み、そのまま貼れる形にする。
4. **数値は実測値を検証済みのものだけ**、信頼区間つきで書く。未確認事項は必ず「要確認」と明記し、確定事実と混ぜない。
5. **誤りが確定した過去文書は必ず差し替える**。古い入力を渡すと誤りが伝播する（実例：偽陽性を主張として抱えた初稿を渡しかけた）。
6. **返ってきたアウトプットは測定側で検証**してから採用する（数値整合・実行可能性・工数見積り）。往復ループを前提に設計する。

## 文書テンプレ（共通骨格）

```
# [受け手] 入力：[目的を1行で]
冒頭：この文書の用途・受け手の役割・末尾にプロンプトがある旨
---
## 1. 前提（大会/プロジェクトの構造、締切、評価軸）
## 2. 確定した事実（実測値・CIつき。表で一望できると良い）
## 3. 資産（すぐ使えるツール・文書・データ）
## 4. 制約と体制（役割分担、技術制約、スキルレベル、期間）
## 5. 未解決論点（受け手に解いてほしい緊張関係を明示）
---
## ★ コピペ用プロンプト（コードブロック）
```

## 目的別のプロンプト設計

### (a) 赤チームレビュー依頼
- 役割宣言：「褒めるのが目的ではなく、論理と統計の穴を最大限あぶり出す」
- **既知の論点リストを渡し「これ以外を探せ」と指定**（既知の再指摘に枠を使わせない）
- 出力形式指定：「指摘リスト（優先度つき）→推奨アクション」
- 縛り：数値を動かすな／推測を事実として書くな／レビュアー自身も過大主張するな

### (b) 戦略立案依頼
- 役割宣言：「◯◯の戦略参謀」
- **解いてほしい緊張関係を明示的に列挙**（労力配分・方針選択・鶏卵問題・撤退基準など）
- 出力を番号つきで指定（全体戦略／意思決定／週次プラン／リスク分岐／最小勝ち筋）
- 縛り：確定事実を覆す提案禁止／実行者のスキルレベルで実行可能な粒度／抽象論禁止・次アクションまで具体化

### (c) 実装・制作依頼（Cowork等）
- 成果物の形式を厳密に指定（フォルダ構成・ファイル名・契約＝関数シグネチャ）
- 技術制約を明記（オフライン実行・時間制限・フォールバック必須など）
- **採否判定の基準と場所を予告**（「別途、評価側で N=◯・有意差で判定」）＝作る側に判定させない

## 検証ループ（返ってきたら）

- 数値が入力と一致しているか照合（動かされていたら差し戻し）
- 提案タスクの工数を測定側で見積もり（「N=500は何分」レベルで具体化）
- 提案に含まれる未検証の前提を抽出し、次の実験候補に積む
- 採用した意思決定は根拠ごと文書化（それ自体が次のハンドオフの§2になる）

## 落とし穴

- **鮮度切れ**：検証で結論が変わったのに古い入力文書を渡す。→ 結論が変わったら即、訂正版を作り旧版は使用禁止と明記。
- **確定と未確認の混在**：締切・ルールなど未確認情報を確定事実の顔で書く。→ 「要確認」タグを徹底し、計画側にも「W1で確認するまで仮置き」と伝播させる。
- **プロンプトの縛り不足**：縛りが無いと受け手は数値を丸めたり、範囲外の推測を事実のように書く。
- **役割の越境**：作る側に採否判定をさせる、考える側に実測なしの数値主張をさせる。判定は必ず測定側で。
